# Архитектура проекта и структура каталогов (docs/spec/architecture.md)

## 1. Архитектурная карта проекта

```
├── src/                               # ИСХОДНЫЙ КОД ПРИЛОЖЕНИЯ (Namespace: App\)
│   │
│   ├── core/                          # Системное ядро и инфраструктурный слой
│   │   ├── database/                  # Подключение к базе данных
│   │   ├── models/                    # Доменные сущности и DTO (Data Transfer Objects)
│   │   ├── repositories/              # Слой прямого доступа к данным (ТОЛЬКО здесь SQL!)
│   │   └── tasks/                     # Фоновые процессы и воркеры
│   │
│   ├── services/                      # Сервисный слой (ВСЯ бизнес-логика здесь)
│   │
│   └── web/                           # Веб-интерфейс API
│       ├── middleware/                # Промежуточные обработки запросов
│       ├── controllers/               # Контроллеры (принимают JSON -> вызывают сервис -> отдают JSON)
│       └── routes/                    # Карты сопоставления URL
│
└── tests/                             # Автоматические тесты (требование ТЗ)
    ├── Unit/                          # Модульные тесты математики рейтинга и лимитов
    └── Feature/                       # Сквозные тесты API
```

## 2. Архитектурные правила

1. **Запрет SQL вне репозиториев:** Ни Контроллер, ни Сервис не имеют права выполнять прямые SQL-запросы (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).
2. **Изоляция бизнес-правил:** Контроллеры не содержат формул расчета рейтинга и проверок прав на начисление баллов — они лишь делегируют выполнение соответствующему Сервису.
3. **Атомарность операций с баллами:** Любое изменение рейтинга или баланса (списание АР за дедлайн, начисление БОА) обязано производиться внутри базы данных атомарно с фиксацией записи в журнале аудита транзакций.
4. **Использование репозиториев:** Только внутри сервисов разрешено обращаться к репозиториям.
